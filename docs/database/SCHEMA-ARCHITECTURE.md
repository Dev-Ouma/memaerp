# MEMA ERP Database and Schema Architecture

**Status:** Implemented and runtime-verified on PostgreSQL 16.14; CI/production certification remains required on the target PostgreSQL 17  
**Database:** PostgreSQL 17  
**Authoritative decisions:** `PLAN/01-ARCHITECTURE-DECISIONS.md` ADR-003 and ADR-012  
**Detailed design:** `PLAN/03-DATA-ARCHITECTURE.md`

## 1. Scope and completion boundary

This deliverable establishes the database foundation used by every ERP module. It completes schema ownership, identifier and tenant conventions, integrity primitives, audit immutability, document metadata, finance ledger primitives, timetable exclusion constraints, backup/restore automation, and database-level verification.

It does not pre-create every Phase 2–5 business table. Those tables belong to their module migrations and must follow the conventions and automated checks defined here. Empty schemas such as `hr`, `research`, and `analytics` are intentional extraction and ownership boundaries until their scheduled modules are implemented.

## 3. Universal record contract

Domain records use UUID identifiers generated by the application UUIDv7 service. Records carry or unambiguously derive an `institution_id`. Ordinary mutable records carry `created_at`, `updated_at`, `created_by`, and `updated_by`; retention-governed records add `deleted_at`. Actor fields are nullable for system migrations and imports but reference `iam.users` when present.

Join/reference records whose tenant is functionally determined by their parent may derive institution context instead of duplicating it. Current approved derivations are:

- grade band → grading scale → institution;
- curriculum course → curriculum version → institution;
- course prerequisite → owning course → institution;
- permission-role grant → role → institution;
- globally governed permission catalogue entries are not institution-owned.

All new migrations must preserve this contract. A new table lacking both an institution column and a documented derivation fails review.

## 4. Tenant isolation and uniqueness

Tenant-scoped public identifiers use composite uniqueness. Application numbers, student numbers, invoice numbers, receipt numbers, and provider transaction references may be reused by another institution but never within the same institution. Hot indexes lead with `institution_id` so authorization scope and tenant predicates remain indexable.

The application determines institution context from the authenticated request/job. A client-supplied institution identifier is never trusted without authorization. Database constraints are the final referential-integrity layer; policies and scoped queries remain mandatory.

## 5. Canonical person spine

`student.persons` is the immutable identity anchor. Applicants, students, employees, alumni, credentials, invoices, payments, and documents reference one person rather than creating module-specific copies. Partial unique indexes deduplicate national and passport identifiers when those values are present, and trigram indexing supports governed duplicate review.

Hard-deleting a person is prohibited operationally once dependent academic, financial, employment, or audit evidence exists. Duplicate resolution must be a separately authorized and audited merge workflow.

## 6. Financial integrity

### Journal truth

`finance.journals` owns posting state and `finance.journal_entries` owns debit/credit lines. A deferred PostgreSQL constraint trigger checks a posted journal at transaction commit:

- at least two entries exist;
- total debit equals total credit exactly;
- each line has either a positive debit or positive credit, never both;
- posted/reversed journals cannot be edited or deleted;
- journal entries are append-only.

Corrections use a new journal whose `reversal_of_id` identifies the original. One original journal can have only one direct reversal.

### Student ledger

`finance.student_ledger_entries` records charges, payments, credits, refunds, reversals, and adjustments. Entries are append-only and may link to invoices, payments, terms and GL journals. `finance.student_balances` and `finance.invoice_ledger_balances` derive balances from entries; no new code may treat mutable invoice balance columns as accounting truth.

Existing `finance.invoices.amount_paid` and `balance` columns remain temporarily for expand/contract compatibility. Their removal requires: dual-write reconciliation, consumer migration to the ledger views, production comparison evidence, then a later contract migration.

### Payment evidence

Provider references are unique per institution. Allocations connect a payment to an invoice and ledger entry. Receipts are separately identifiable and voided with evidence rather than deleted. Unmatched or inconsistent provider events enter `finance.reconciliation_exceptions` and cannot disappear silently.

## 7. Scheduling concurrency

`course.teaching_slots` uses PostgreSQL GiST exclusion constraints over half-open timestamp ranges. Active slots cannot overlap for the same room or lecturer within an institution. Adjacent slots are allowed because `[start, end)` does not overlap `[end, next_end)`.

Application-level clash checks provide friendly errors, but the exclusion constraint is the concurrency guarantee. Registration capacity similarly has a database check ensuring `0 <= enrolled_count <= max_capacity`; the eventual enrollment service must combine row locking with the documented Redis contention-shedding lock.

## 8. Audit governance

`audit.activity_log` is range-partitioned by `occurred_at`. PostgreSQL triggers reject `UPDATE` and `DELETE` with SQLSTATE `42501`. JSONB GIN indexes support field investigations, while actor, subject, module and correlation indexes support operational trace reconstruction.

`php artisan audit:partitions --months=12` creates monthly partitions ahead of demand under a PostgreSQL advisory lock. The scheduler runs it monthly. `audit.partition_health` exposes installed partitions, bounds, and storage size. Operators must alert on writes landing in the default partition because they indicate failed partition maintenance or out-of-range timestamps.

## 9. Document metadata and retention

`documents.files` stores metadata only; object bytes live in S3-compatible storage. Every record includes classification, purpose, media type, size, storage key, SHA-256 checksum, malware status, retention date and legal-hold state. `documents.file_versions` makes object changes traceable without overwriting prior metadata.

Protected files are private by default. Download authorization is re-evaluated before issuing a short-lived signed URL. Legal hold overrides automated disposal. A metadata row may not claim a clean, available object until upload and malware scanning complete successfully.

## 10. Migration policy

1. Never edit a migration after it may have run in another environment.
2. Use expand/backfill/switch/contract for renames, required columns, and type changes.
3. Keep schema changes and large data backfills in separate releases.
4. Every foreign key states its delete behavior deliberately.
5. Every invariant that must survive imports and jobs belongs in PostgreSQL.
6. Migration rollback must be exercised before merge. A rollback that would destroy valid new tenant data must fail loudly rather than discard it.
7. Large-table constraints are introduced with production-safe validation sequencing when data volume makes a blocking validation unsafe.

## 11. Backup, restore and recovery

`make backup` creates a PostgreSQL custom-format dump plus a SHA-256 checksum. Production storage must encrypt and copy the artefact off-host; the script does not embed credentials or encryption keys.

`make fresh-restore-test` performs the Gate 0 restore drill against the explicitly named scratch database. It:

1. creates a fresh custom-format backup;
2. drops only the configured scratch database;
3. restores with `--exit-on-error`;
4. compares every application table's row count between source and restored databases;
5. reports elapsed recovery time;
6. removes the scratch database and temporary dump.

Production targets remain RPO ≤ 5 minutes through WAL archiving and RTO ≤ 4 hours. A scheduled dump alone does not satisfy Gate 0; a timed, reconciled restore report is required.

## 12. Verification commands

```bash
make database-verify
make quality
make backup
make fresh-restore-test
```

`make database-verify` rebuilds the database, runs the architecture integration suite, rolls back the four foundation migrations, and reapplies them. CI must run the same workflow against PostgreSQL 17.

## 13. Remaining module-owned work

The foundation is complete only as infrastructure. Later modules still own their detailed tables, services, data migrations and business-rule tests. In particular, graduation, HR/payroll, procurement, research, CMS and analytics remain intentionally unscheduled here. Creating speculative tables for those modules would encode unapproved rules and violate the implementation brief.

The unresolved module-boundary decision in `docs/architecture/ADR-REVIEW-001-module-boundaries.md` affects PHP dependency enforcement, not the PostgreSQL integrity structures described here.
